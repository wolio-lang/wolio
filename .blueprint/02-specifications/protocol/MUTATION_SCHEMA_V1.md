# Structured mutation schema V1

This document is normative for M04. It is independent of any AI client,
editor, shell, or orchestration tool. The JSON-lines transport is defined by
`LOCAL_PROTOCOL_V1.md`; this defines the `plan` method's `params` payload.

## 1. Canonical encoding

Requests and responses use UTF-8 JSON. Object keys are sorted lexicographically
for hashing. Unknown object keys are rejected. Arrays preserve order unless a
field says it is a set; set arrays are sorted by their canonical JSON value.
Integers are signed decimal JSON integers in the CORE_V1 Int range. No floats,
null values except create preconditions, duplicate object keys, comments, JSON patches, byte offsets, source
fragments, or arbitrary file paths are accepted in mutation payloads.

The canonical mutation hash is SHA-256 over:

```text
length_prefix("wolio.mutation.v1") || length_prefix(base_snapshot)
  || length_prefix(canonical_json(params))
```

Length prefixes follow INTERFACE_CONTRACTS. Scope and capabilities are included.
The plan hash is independent of transport request ID, timestamps, actor names,
and diagnostic wording. String values are UTF-8 and preserve case. Paths are
normalized project-relative paths only when used by scope; a mutation targets a
semantic declaration ID, not a path.

## 2. Plan envelope

```json
{
  "intent": "add a bounded total operation",
  "operations": [],
  "scope": {"paths": ["src/main.wol"], "symbols": []},
  "capabilities": []
}
```

Required fields are `intent`, `operations`, `scope`, and `capabilities`.
`intent` is non-empty human-readable context and is provenance, never semantic
authority. `operations` is non-empty. `scope.paths`, `scope.symbols`, and
`capabilities` are arrays; empty scope matches nothing; omission fails validation. Capabilities are
declared names and are checked against the project policy.

## 3. Operation envelope

Every operation has exactly `kind`, `target`, `expected_old_hash`, and `payload`.
`target` is omitted only for `create_declaration`; `expected_old_hash` is null
only for create. Payload shape is determined by `kind`:

```text
create_declaration
replace_implementation
replace_contract
rename_symbol
move_symbol
add_test
delete_symbol
```

The service rejects conflicting operations, unknown kinds,
and an operation whose target is outside the declared scope. A plan is rejected
if its operations cannot be rendered into a canonical V1 AST without inventing
language constructs.

## 4. Typed AST values

Expressions are tagged objects with exactly one `kind` plus the fields listed:

```text
int       {kind, value}
string    {kind, value}
bool      {kind, value}
name      {kind, path: [identifier, ...]}
unary     {kind, op: "!"|"-", value}
binary    {kind, op, left, right}
call      {kind, path, args: [expr, ...]}
record    {kind, path, fields: [{name, value}, ...]}
if        {kind, condition, then, else}
match     {kind, subject, arms: [{pattern, value}, ...]}
field     {kind, value, name}
unit      {kind}
block     {kind, lets: [{name, value}, ...], value}
```

Patterns are tagged objects:

```text
constructor {kind, path, binding?}
bool        {kind, value}
```

Types are tagged objects:

```text
name {kind, path}
application {kind, path, args: [type, ...]}
```

Declaration, contract, implementation, and test payloads use these values and
the exact CORE_V1 names. Duplicate named fields, arms, set clauses and bindings
fail; repeated positional argument expressions and predicate clauses are legal.
Source spans are generated by
the renderer and are not accepted from the agent.

## 5. Operation payloads

`create_declaration` requires `declaration_kind`, `module`, `name`, and a typed
payload matching the kind. `replace_implementation` requires `body` (a block or
expression appropriate to CORE_V1). `replace_contract` requires the complete
contract, including all `requires`, `ensures`, `effects`, `dependencies`, and
`errors` clauses; omission means an empty set and is never auto-filled.
`rename_symbol` requires `new_name`; `move_symbol` requires `new_module`.
`add_test` requires `name`, `operation`, and typed `body`. `delete_symbol` has
an empty payload. Implementations cannot modify declarations, contracts,
manifest, lockfile, policy, or generated files through this schema.

The renderer is deterministic, uses CORE_V1 syntax, and preserves unrelated
comments/source. The output is checked again; rendered text is not an input
authority.

## 6. Identity and lifecycle

### Complete declaration shapes

All fields below are required; `?` alone marks optional fields. Identifiers and
paths obey CORE_V1. Paths are nonempty arrays of identifiers; arrays are ordered
unless designated sets. No source spans are supplied.

```text
create payload = {module, declaration}
nominal declaration = {kind:"nominal", name, public:boolean, type}
record declaration = {kind:"record", name, public:boolean, fields:[{name,type}]}
enum declaration = {kind:"enum", name, public:boolean, variants:[{name,type?}]}
operation declaration = {kind:"operation", name, public:boolean,
                         parameters:[{name,type}], returns:type, contract}
implementation declaration = {kind:"implementation", name, body:block}
test declaration = {kind:"test", name, operation:path, body:block}
contract = {requires:[expr], ensures:[expr], effects:[path],
            dependencies:[path], errors:[path], intent?:string}
replace_implementation payload = {body:block}
replace_contract payload = {contract}
rename_symbol payload = {new_name:identifier}
move_symbol payload = {new_module:identifier}
add_test payload = {module:identifier, name:identifier, body:block}
delete_symbol payload = {}
```

These shapes supersede the prose shorthand in section 5: create uses the
declaration's `kind`, not a separate declaration_kind. `add_test.target` is the
operation tested; its expected hash is that operation's hash. The resulting
test identity must be vacant. Create has no target and expected_old_hash is
null. Other operations require a target and its normalized declaration hash.
Implementation replacement targets an implementation; contract replacement
targets an operation. Rename/move of an operation moves its implementation too.
Creating an operation and its implementation uses two create operations in one
plan. A plan is validated as a whole; references resolve in the resulting graph.
Mutation cannot create modules/imports or edit manifests in this V1 schema:
destination modules/imports must exist; unavailable imports reject the plan.

Effects/dependencies/errors/capabilities/scope arrays are sets, sorted canonically
without duplicates. Record fields, parameters, variants, match arms, predicates,
lets and positional args preserve order. Binary op is exactly a CORE_V1 binary
operator. Blocks are only legal in CORE_V1 block positions; `unit` renders
`unit()`. Type application accepts only builtin generic constructors. Int MIN
renders as unary minus over magnitude 9223372036854775808; other int literals
render canonically. This does not introduce signed-literal syntax to CORE_V1.

Canonical AST diff is a sorted array of `{id,before,after}` entries over changed
declarations, with normalized AST objects and null for absence. IDs sort in byte
order; spans/comments are excluded; semantic names resolve to IDs. Hash using
the length-prefixed domain `wolio.ast-diff.v1` plus canonical JSON. Snapshot and
rendered-content hashes additionally bind formatting and unrelated source.
Request limit is 1 MiB UTF-8 per JSON line, 256 operations per plan and AST depth
128; exceeding limits is a usage/configuration error before staging.

Create uses the deterministic semantic key. Rename or module move produces an
explicit old/new identity link and updates references atomically. It does not
claim identity preservation. Delete then recreate may produce the same definition
ID, but evidence is bound to `(ID, declaration_hash, snapshot_hash)` and cannot
be reused merely because the ID matches.

## 7. Rejection contract

Raw text, patches, arbitrary paths, unknown JSON fields, unsupported grammar,
missing required fields, duplicate keys, non-canonical sets, and attempts to
change approval tier are rejected before mutation with structured diagnostics.
The agent supplies no approval tier; the service derives it from the semantic
diff and the approval matrix.
